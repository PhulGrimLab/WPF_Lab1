# RTOS 시뮬레이터와 실제 RTOS 차이 정리

이 문서는 현재 Wpf.Lib.RTOS가 "무엇을 잘 흉내 내는지"와 "실제 RTOS와 어디가 다른지"를 초보자 관점에서 쉽게 정리한 비교표입니다.

---

## 1. 한 줄 요약

현재 라이브러리는 "RTOS 개념 학습용 시뮬레이터"로는 매우 유용하지만, 하드 실시간 보장을 요구하는 실제 제품 RTOS 대체 용도로는 적합하지 않습니다.

---

## 2. 항목별 차이

| 항목 | 현재 Wpf.Lib.RTOS | 실제 RTOS(일반적) | 영향 |
|---|---|---|---|
| 스케줄링 기반 | .NET Task + TimeSpan + DateTimeOffset | 하드웨어 타이머 tick + 커널 스케줄러 | 지터와 지연이 상대적으로 큼 |
| 선점 방식 | 협력형 양보(ShouldYield) 중심 | 인터럽트 기반 강제 선점 가능 | 태스크가 양보 코드를 안 넣으면 선점 체감이 약함 |
| 우선순위 | 실행 후보 정렬 기반 우선순위 | 커널 준비 큐 우선순위 + 컨텍스트 스위치 | 우선순위 역전 대응이 제한적 |
| 시간 정확도 | OS 스케줄러와 GC 영향 받음 | 하드 실시간 목표(플랫폼 의존) | 엄격한 deadline 보장 어려움 |
| ISR(인터럽트) | 없음 | ISR + Deferred Work(Task/Thread) 구조 | 디바이스 이벤트 즉시 처리 모델 부재 |
| 메모리 모델 | GC 기반 동적 메모리 | 정적/풀 메모리 선호 | 할당 지연, GC pause 가능성 |
| 동기화 primitive | Semaphore/Mutex/EventFlags/Queue 시뮬레이션 | 커널 원자성 + ISR-safe API | 극한 동시성 상황 동일성 보장 어려움 |
| 보호 경계 | 라이브러리 레벨 lock | 커널 모드 스케줄링 보호 | 시스템 전체 보호 범위가 다름 |
| 전력/저전력 | 별도 전력 상태 제어 없음 | idle hook, tickless idle 등 지원 | 임베디드 전력 최적화 학습에는 한계 |
| MPU/권한 분리 | 없음 | 메모리 보호/권한 분리 가능 | 안전성/보안 시나리오 검증 한계 |

---

## 3. 그래도 현재 구조가 강한 부분

1. 태스크 주기/우선순위/OneShot/Overrun 개념을 학습하기 좋습니다.
2. 동기화 primitive의 사용 패턴을 UI와 함께 시각적으로 확인하기 좋습니다.
3. Snapshot/Trace 기반으로 "관찰 가능한 스케줄링" 실험이 쉽습니다.
4. WPF 데모와 연결되어 초보자가 동작을 빠르게 체감할 수 있습니다.

---

## 4. 실제 RTOS에 더 가깝게 가려면 (권장 로드맵)

1. 강제 선점 실험층 추가
- 현재 ShouldYield 기반 협력형 외에, 장시간 실행 태스크를 time-slice 단위로 강제 분할하는 실험 모드 추가

2. 시간원 분리
- DateTimeOffset.Now 대신 monotonic clock(Stopwatch 기반) 중심으로 실행 시각 계산

3. 고정 메모리 정책 옵션
- 메시지 큐/로그 버퍼에서 고정 크기 정책을 기본값으로 강화

4. ISR 유사 이벤트 채널 도입
- 외부 이벤트 입력 채널을 두고, ISR-safe API처럼 제약된 호출 경로 제공

5. 우선순위 역전 실험 시나리오 강화
- Mutex 대기 체인/중간 우선순위 태스크 간섭 시나리오 테스트 추가

---

## 5. 프로젝트에서 이 문서를 어떻게 쓰면 좋은가

1. 데모 목적 설명
- "실제 RTOS 구현"이 아니라 "RTOS 동작 원리 학습"임을 먼저 명시

2. 코드 리뷰 기준 정렬
- 정확도(실시간 보장)보다 관찰성(로그/스냅샷)과 안정성(예외/정리) 중심으로 리뷰

3. 테스트 기대치 정렬
- deadline miss 0 보장 같은 하드 실시간 기준 대신,
  정책대로 동작하는지(우선순위/타임아웃/해제 경로) 검증 중심으로 테스트

---

## 6. 결론

Wpf.Lib.RTOS는 "실제 RTOS와 동일한 커널"이 아니라,
"RTOS 핵심 개념을 안전하게 실험할 수 있는 시뮬레이터"로 보는 것이 정확합니다.

이 기준으로 문서와 테스트를 구성하면, 초보자 학습 효과와 코드 유지보수성이 크게 좋아집니다.

## 7. 2026-05-22 FAQ 보강

### Q1. UI 스레드가 항상 고정이면 선점 의미가 없나요?

아닙니다.

이 프로젝트의 선점은

1. UI 스레드 선점이 아니라
2. RTOS 태스크 간 우선순위 선행(협력형 양보)

을 의미합니다.

### Q2. 왜 UI 스레드를 선점 판정에서 제외하나요?

이유는 2가지입니다.

1. WPF UI 스레드는 화면 이벤트 루프 경계라 역할이 다름
2. RTOS 학습 포인트(우선순위/양보/동기화)를 태스크 경계에서 명확히 보기 위함

### Q3. 그럼 현재 시뮬레이터의 강점은 무엇인가요?

1. 정책(우선순위/주기/오버런/양보)을 빠르게 실험 가능
2. 스냅샷/로그/TID로 관찰 가능
3. 테스트 러너로 동작 검증 가능

즉 "학습/검증 속도"가 핵심 강점입니다.

## 8. 실무 적용 가이드 (과대해석 방지)

실무에서 이 코드를 사용할 때는 아래 기준으로 해석하는 것이 안전합니다.

1. 가능한 것
    - 정책 검증
    - 동기화 패턴 학습
    - 오류/종료/정리 경로 점검

2. 불가능하거나 제한적인 것
    - 하드 실시간 deadline 보장
    - ISR/문맥교환 수준 커널 동작 검증

3. 문서/코드 리뷰 문장 권장
    - "RTOS 커널 구현" 대신
    - "RTOS 스타일 학습 시뮬레이터"로 명시
